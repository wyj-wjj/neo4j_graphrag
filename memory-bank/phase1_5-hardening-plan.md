# 阶段 1.5：阶段一健壮性加固方案

> 文档状态：已实施并通过本地验收（2026-07-14）
> 制定日期：2026-07-14
> 阶段定位：阶段一完成后、阶段二开始前
> 目标：先补齐上下文、记忆、并发、恢复、流式、治理和评测闭环，再接入真实业务与分布式基础设施。
> 权威关系：`phase1_env_checklist.md` 仍是阶段一权威设计文档；本文只记录阶段 1.5 的问题、根因、加固方案和验收门槛，不改变阶段二边界。

实现结果以 `architecture.md` 为准。里程碑 A–E 已完成；当前本地验收为 Ruff、mypy、95 个 pytest
通过（1 个真实依赖测试因无 Docker 跳过）、86.43% 覆盖率、阶段一 Golden Set 和
`memory-reliability-v1` 全部门槛通过。真实百炼与生产集群容量仍不是本地 Fake 指标可以替代的上线证据。

## 1. 核心结论

当前阶段一已经具备模块化单体、Port/Adapter、MySQL 真理源、Redis Checkpoint、三路 GraphRAG、
MySQL 最终授权、引用与拒答、Tool 风控、文档入库、Fake 业务边界和完整 CI。它是可靠的功能基线，
但还不能直接等同于生产级 Agent。

阶段 1.5 不增加真实业务范围，也不拆微服务。核心任务是让现有能力在长会话、并发请求、进程重启、
状态升级、依赖故障和恶意输入下仍保持确定、可恢复、可审计和可评测。

严格按照 `enterprise_multi_agent_architecture.md` 的“生产级核心难题与硬核解决方案”检查，当前主要缺口集中在：

- 会话历史已保存，但没有进入 Agent 与 Query Rewrite 的主调用链。
- Agent State 能持久化，但尚未形成真正的安全中断、恢复和版本迁移机制。
- 没有统一的 Token 预算、上下文组装器、滚动摘要和结构化任务状态。
- 没有长期记忆的写入、确认、冲突、过期、纠错和删除治理。
- 同一会话的并发请求缺少幂等键、顺序号和乐观并发控制。
- 当前 SSE 是完整答案生成后再切片发送，不是真正降低 TTFT 的模型流式链路。
- 当前 Supervisor 主要是规则路由，尚未形成多级路由和单轮多 Agent 收敛。
- 评测偏重单轮检索与合成数据，尚未覆盖长会话记忆、恢复、并发和摘要失真。
- Prompt、模型和上下文策略仍缺少统一版本治理与回滚基线。

## 2. 外部参考文章的价值与使用边界

参考文章：[AI Agent 记忆管理实战：上下文窗口、RAG 与会话持久化怎么做才稳定](https://htmlpage.cn/topics/ai/ai-agent-memory-management-practice)。

### 2.1 有参考价值的内容

文章提出的以下思想与本项目方向一致，应吸收进阶段 1.5：

1. 记忆不是把全部聊天记录拼进 Prompt，而应区分短期记忆、长期记忆和外部证据。
2. 工作记忆应拆成自然语言摘要与结构化状态；硬约束不能只保存在摘要里。
3. 每轮请求应经过统一的加载状态、压缩、检索、组装、生成、校验和持久化管线。
4. 上下文窗口应按 Token 预算和信息优先级管理，而不是只按固定轮数截断。
5. 长期记忆必须有明确的写入标准、TTL、覆盖、纠错和用户删除机制。
6. 外部证据必须携带来源、时间、适用范围和引用要求。
7. 多用户会话必须实现隔离、幂等和并发一致性。
8. 记忆效果必须通过重复追问率、约束违反率、长会话成功率、引用率和上下文 Token 等指标验证。

### 2.2 需要按本项目边界落地的内容

- 在缺少本项目评测数据时，采用文章建议的 `30% / 20% / 40% / 10%` 作为
  `context-policy-v1` 的初始默认配比；它是可运行、可比较的实验基线，不是权威结论或永久硬编码。
- 初始配比只作用于已经为模型输出预留空间后的可用输入 Token 预算；实际使用量仍受模型窗口、问题类型、
  安全硬约束和有效证据数量影响。完成 Memory & Reliability Golden Set 后，必须根据指标按策略版本微调。
- 最近若干轮只是一种候选来源，不能代替 Token 预算、任务相关性和结构化约束。
- 用户权限、VIP、订单状态等业务事实必须从 MySQL/IAM/业务 Port 实时读取，不能变成模型可写的长期记忆。
- 阶段 1.5 不采用 MQ Write-behind 作为会话真理源；在 Kafka 尚未落地时，关键状态必须先可靠写入 MySQL。
- Retrieval Rewrite、HyDE、Multi-Query 和长期语义记忆必须由评测证明收益后再启用，不能为了“更智能”默认增加成本和幻觉面。
- 该文章是辅助工程参考，不覆盖本仓库的权威设计、安全规则和阶段边界。

## 3. 目标记忆模型

阶段 1.5 将上下文与记忆拆成六层。不同层级必须有独立的所有者、真理源、TTL、注入规则和审计规则。

| 层级 | 典型内容 | 真理源 | 生命周期 | 模型是否可修改 |
| --- | --- | --- | --- | --- |
| 请求上下文 | `tenant_id`、`user_id`、roles、request/run ID、渠道 | JWT/IAM 和服务端 | 单请求 | 不可修改 |
| 工作记忆 | 当前意图、已访问节点、证据 ID、Tool 结果、错误 | Redis Checkpoint | 单次运行 | 仅允许受控字段更新 |
| 会话记忆 | 最近消息、滚动摘要、开放问题、当前目标 | MySQL，Redis 仅作热投影 | 单会话 | 只能通过应用服务更新 |
| 任务记忆 | 退款草单、待补材料、审批节点、幂等结果 | MySQL 业务状态机 | 跨请求、跨重启 | Agent 只能提出草单或命令 |
| 用户长期记忆 | 用户明确确认的稳定偏好和长期目标 | MySQL | 跨会话，可过期/删除 | 默认关闭自动写入 |
| 外部证据 | RAG Chunk、图路径、数据库或 Tool 权威结果 | 对应权威系统 | 当前回答 | 只读，每次重新授权 |

### 3.1 不可混淆的边界

- 会话历史不等于 Agent Checkpoint。历史用于理解对话，Checkpoint 用于恢复执行。
- 用户画像不等于长期记忆。权威画像来自业务系统，长期记忆只保存允许记住的用户偏好。
- 检索证据不等于用户记忆。证据按当前身份重新检索和授权，不得跨请求盲目复用原文。
- 自然语言摘要不等于结构化状态。摘要可以压缩语境，结构化状态必须保存硬约束和任务进度。
- 模型输出不等于事实。未经确认或权威来源验证的模型推测不得写入长期记忆。

## 4. 目标上下文管线

每个聊天请求统一经过以下阶段，禁止由不同 Agent 自行拼接上下文：

```text
鉴权并建立不可变 RequestContext
    → 按 client_turn_id 幂等接收本轮消息
    → 加载 Session State、最近消息和安全恢复点
    → 校验 state_version 与 session revision
    → 必要时更新滚动摘要，但独立保留结构化约束
    → 根据当前问题检索相关历史和外部证据
    → Context Assembler 按 Token 预算组装
    → Agent/模型生成
    → 执行引用、约束、权限和输出 Schema 校验
    → 原子持久化消息、状态、运行结果和新 revision
    → 保存新的安全 Checkpoint 与 Context Manifest
```

### 4.1 上下文优先级

上下文组装应遵守以下优先级：

1. 系统安全策略、Tool 风险规则和输出协议：不可删除。
2. 不可变身份、权限和租户上下文：不可由模型生成或覆盖。
3. 当前任务的结构化状态、硬约束和幂等结果：不可被摘要替代。
4. 当前用户问题及必要澄清字段。
5. 当前问题相关的权威外部证据和 Tool 结果。
6. 最近几轮原始对话。
7. 滚动摘要和相关较早历史。
8. 低相关背景信息：预算不足时优先丢弃。

必须预留输出 Token，输入上下文不能占满模型窗口。预算计算以模型 Tokenizer 或经过校准的 Token 估算为准，
不能继续只依赖字符数。

#### 4.1.1 阶段 1.5 初始预算配比

在尚无本项目长会话评测结果时，`context-policy-v1` 采用以下默认目标配比。比例针对“扣除模型输出预留后”的
可用输入 Token 预算，四个分区合计 100%。

| 上下文分区 | 初始目标比例 | 包含内容 |
| --- | ---: | --- |
| 短期原文 | 30% | 最近且与当前问题相关的用户/助手消息原文 |
| 工作记忆 | 20% | 滚动摘要、结构化 Conversation State、任务进度和开放问题 |
| 外部证据 | 40% | 已授权 RAG 证据、必要图路径和经过验证的 Tool 结果 |
| 系统协议 | 10% | 系统安全策略、不可变身份/权限摘要、当前问题、Tool/输出协议和失败规则 |

该配比是目标值而不是每轮必须填满的定额，执行时遵守以下规则：

1. 系统安全规则、当前问题、不可变权限上下文和结构化硬约束具有最低保障，不得为了满足比例而截断；
   超过目标比例时优先压缩低相关历史，再移除低价值或重复证据。
2. 没有知识检索需求的 FAQ、澄清或纯任务状态请求，不得为了填满 40% 而注入无关证据；空闲预算可以按需让给
   短期原文或工作记忆，也可以保持不用。
3. 证据密集型问题可以临时提高外部证据比例，但每条证据仍必须通过授权、去重、有效期和相关性校验；
   数量不足时不得用低质量证据凑配额。
4. 结构化状态中的金额、权限、地域、有效期、否定条件和审批状态不得被自然语言摘要替代。
5. 每次运行在 Context Manifest 中记录目标比例、实际 Token、借用/回收情况、截断原因和 `context_policy_version`。
6. 后续每次调整都必须产生新策略版本，并使用同一评测集比较任务成功率、约束违反率、引用率、
   长会话成功率、平均上下文 Token 和延迟；不得静默修改现有版本。

第一轮评测至少比较当前 `30/20/40/10` 基线与两个受控候选策略，再决定是否修改默认值。评测前保持该基线稳定，
避免一边开发一边调整比例导致结果不可比较。

### 4.2 Context Manifest

每次运行生成可审计但不包含敏感原文的 Context Manifest，至少记录：

- Prompt、模型、Agent State 和上下文策略版本。
- 每个上下文分区的 Token 数量。
- 使用的消息 ID、摘要版本、结构化状态版本和证据 ID。
- 被丢弃或压缩的信息类别及原因。
- 检索、授权、去重、Rerank 和最终引用数量。
- 是否发生降级、修复、追问或拒答。

Manifest 用于回放和评测，不得记录完整 Token、密码、地址、证件号或未经脱敏的原文。

## 5. 当前问题、根因与解决方案

### 5.1 会话历史没有进入 Agent 主链路

**当前问题**

MySQL/内存 Session Service 能保存并查询历史，但聊天 API 调用 Agent 时只传入当前问题。
`AgentState.chat_history`、GraphRAG `history` 和 Query Rewrite 虽已定义，主要执行链仍使用空历史。

**根因**

- 会话持久化与 Agent 上下文组装被分别实现，缺少统一 Context Assembler。
- 阶段一验收主要验证历史可查询，没有验证后续问题是否真正使用历史。

**解决方案**

- 在应用服务层建立唯一的上下文加载入口，Agent 不直接查询 Session Repository。
- 从已授权会话加载有限最近消息、摘要和结构化状态，并显式传入 Agent State。
- Query Rewrite 只使用允许进入当前上下文的历史，不直接读取全部消息。
- 增加多轮指代、历史冲突、跨用户会话和关闭会话回归测试。

**验收标准**

- “这个怎么办”等指代问题能够引用正确的前文主题。
- 明确独立问题不会被旧历史错误改写。
- 其他用户或租户的消息进入上下文数量为零。

### 5.2 缺少 Token 预算和统一上下文组装

**当前问题**

当前证据上下文使用字符预算，聊天历史、摘要、任务状态、Tool 结果和证据之间没有统一配额和淘汰策略。

**根因**

- 阶段一聚焦 GraphRAG 证据预算，没有建立全请求级 Context Policy。
- 当前 Fake 模型不会暴露真实模型窗口压力，测试不容易触发溢出。

**解决方案**

- 新增独立 Context Assembler Port/应用服务，统一计算输入预算并预留输出空间。
- 预算、分区上限、摘要阈值、最近轮数上限和丢弃策略全部配置化、版本化。
- 采用“硬约束永不丢、证据按问题选择、历史按相关性和时间选择”的策略。
- 在上下文接近阈值时先压缩低优先级历史，不压缩权限、金额、时间、地域和审批状态等硬字段。

**验收标准**

- 所有测试请求均不超过配置的输入预算。
- 预算不足时的丢弃顺序确定且可通过 Manifest 解释。
- 压缩前后结构化硬约束保持完全一致。

### 5.3 没有“摘要 + 结构化状态”的双层工作记忆

**当前问题**

现有 Agent State 记录本轮执行字段，但没有会话目标、约束、已确认事实、开放问题和任务阶段的稳定结构；
也没有滚动摘要。

**根因**

- 当前对话以单轮问答和单专家结束为主，不需要复杂任务连续性。
- 将执行状态和对话语义状态放在同一个 Agent State 中，会导致字段所有权和生命周期混乱。

**解决方案**

- 引入版本化 Conversation State，至少拆分 `goal`、`constraints`、`confirmed_facts`、
  `open_questions`、`task_stage` 和 `last_processed_sequence`。
- 摘要只保留语境与进展；结构化状态保存可机器校验的硬约束。
- 状态更新必须通过严格 Schema、字段所有权和确定性 Reducer；模型只能返回候选更新。
- 每次摘要保存覆盖的消息范围和来源消息 ID，支持重新生成与回放。

**验收标准**

- 8、12、16 轮测试中，预算、地域、时间、否定条件和审批状态不丢失、不反转。
- 摘要重建后能够定位到其覆盖的原始消息。
- 非法状态更新在写入前被拒绝并产生审计事件。

### 5.4 长期记忆缺少治理

**当前问题**

当前没有跨会话长期记忆；若未来直接增加向量化“用户记忆”，容易把临时信息、模型猜测或敏感内容永久化。

**根因**

- 尚无真实业务数据和用户同意策略，阶段一正确地没有自行推断长期记忆。
- 缺少长期记忆分类、来源、有效期、冲突和删除契约。

**解决方案**

- 阶段 1.5 先定义 Long-term Memory Port、Schema、授权和 Fake/禁用实现，自动写入默认关闭。
- 只允许用户明确确认的稳定偏好、允许保存的长期目标和经权威来源确认的低敏事实成为候选。
- 明确禁止写入一次性需求、模型推测、密码/Token、完整证件信息和未经确认的业务事实。
- 每条记忆记录来源、确认方式、置信等级、有效期、敏感等级、版本和状态。
- 提供查看、纠错、删除、禁用和审计能力；删除必须同步清理派生语义索引。

**验收标准**

- 未确认的模型推测写入长期记忆数量为零。
- 过期、删除或被用户禁用的记忆不再进入上下文。
- 跨用户、跨租户长期记忆污染数量为零。

### 5.5 Checkpoint 尚未形成真正的断点续跑

**当前问题**

系统同时保存 LangGraph Redis Checkpoint 和应用级最终 Agent State，但没有完整的安全恢复入口、节点恢复矩阵、
审批中断恢复或副作用去重闭环。

**根因**

- 当前图是 `Supervisor → 一个专家 → END`，运行很短，阶段一测试主要验证状态成功保存。
- Fake 审批回调与原 Agent Run 没有建立可恢复执行关系。

**解决方案**

- 明确哪些节点是安全 Checkpoint，记录节点、状态版本、已完成副作用和下一合法动作。
- 为 Tool 调用保存稳定 `tool_call_id`、幂等键和结果摘要；恢复时不得重复执行已成功副作用。
- 增加受控恢复用例，只允许同租户、同用户或授权管理员恢复。
- Refund 保持阶段一 Fake，但应能演示 `calculate → create_draft → interrupt → callback → resume`，
  最终仍不得执行真实退款。
- 区分“继续原运行”和“创建新运行重试”，两者使用不同审计语义。

**验收标准**

- 在路由后、检索后、草单后和答案持久化前注入中断，恢复结果与不中断执行语义一致。
- 已成功的写 Tool 在恢复时重复执行数量为零。
- 非法用户不能列举或恢复其他会话的 Checkpoint。

### 5.6 State Version 只有字段，没有迁移机制

**当前问题**

`state_version` 已存在，但缺少版本注册、旧状态迁移、未知未来版本拒绝和迁移测试夹具。

**根因**

- 阶段一只有单一版本，没有真实升级场景。
- Redis TTL 被当作自然淘汰手段，但审批或长期任务可能超过 TTL。

**解决方案**

- 建立显式 State Migration Registry，每个迁移只支持相邻版本并保持可审计。
- 未知未来版本必须 fail closed；无法迁移的状态转人工，不得静默丢字段。
- MySQL 保存最小安全恢复快照和状态版本；Redis 丢失时可恢复到最近安全节点。
- 每个状态版本保存固定 JSON 测试夹具，防止字段重命名或默认值变化破坏恢复。

**验收标准**

- 支持的所有旧版本均可迁移到当前版本。
- 未知未来版本和损坏状态均被明确拒绝，不产生业务副作用。
- Redis 数据丢失后能从 MySQL 安全快照恢复，或给出可追踪的转人工结果。

### 5.7 同一会话缺少幂等和并发一致性

**当前问题**

同一 Session 的快速连续请求、网络重试或多渠道并发可能造成消息重复、顺序变化、状态覆盖和 Checkpoint 竞争。

**根因**

- 当前限流只控制请求数量，不控制同会话写入顺序。
- Session/Message 缺少客户端轮次幂等键、单调序号和状态 revision。
- Checkpointer 的 thread 隔离不能自动解决同一 thread 的并发写冲突。

**解决方案**

- 每个聊天请求要求或生成稳定 `client_turn_id`，并以租户、会话和该 ID 建立唯一约束。
- 每条消息使用会话内单调 `sequence`，不依赖时间戳和随机 ID 推断顺序。
- Session 增加 `revision`，状态更新使用 compare-and-swap；冲突时不自动覆盖。
- 阶段 1.5 优先采用“同一会话单运行”策略：后续请求排队或返回明确 busy/conflict；
  未来确有需求再设计分支合并。
- 重复提交返回已有运行结果或当前状态，不生成第二组消息和 Tool 副作用。

**验收标准**

- 同一 `client_turn_id` 重复提交不会增加消息、Agent Run、Tool Call 或草单数量。
- 并发 2～10 个请求时消息顺序确定，Checkpoint 不发生静默覆盖。
- 不同会话仍可并发运行，不因全局锁互相阻塞。

### 5.8 消息、运行结果和 Checkpoint 的提交边界不完整

**当前问题**

当前 Agent 完成后再追加用户与助手消息；若在模型完成、Checkpoint 保存、消息写入之间宕机，可能出现结果已执行但历史缺失，
或客户端重试导致重复运行。

**根因**

- Agent/Redis/MySQL 无法使用单一数据库事务。
- 尚未定义跨存储的可恢复提交协议。

**解决方案**

- 先在 MySQL 原子创建用户消息和 `agent_run=running`，再开始 Agent 执行。
- 每个运行绑定唯一 `client_turn_id` 和输入 hash。
- 成功时在 MySQL 同事务写助手消息、运行结果、会话 revision 和恢复摘要，再更新可丢失的 Redis 热投影。
- 失败或取消必须写终态；不完整运行由恢复任务识别，不能永久停留在 `running`。
- Redis 失败不能导致 MySQL 已确认消息丢失；MySQL 不可用时不得继续需要长期状态的业务操作。

**验收标准**

- 在每个提交边界注入进程退出后，系统都能判断本轮是未开始、可恢复、已完成或明确失败。
- 不存在“Tool 已成功但运行和幂等记录均不存在”的状态。
- 历史接口只返回顺序明确且状态可解释的消息。

### 5.9 外部证据缺少统一冲突与输出校验

**当前问题**

现有证据包含 Chunk、文档、版本、时间和来源，引用与无证据拒答已实现；但证据冲突、适用范围和生成后约束校验仍较弱。

**根因**

- 当前 Golden Set 以单一确定答案为主，缺少冲突知识和跨版本适用范围样本。
- 生成结果主要通过 Prompt 约束，缺少统一 Answer Validator。

**解决方案**

- 统一 Evidence Bundle，补充有效期、适用范围、权威等级和冲突组。
- 上下文组装前完成去重、版本选择和冲突标记；禁止让模型自行猜测哪个版本有效。
- 输出采用可验证结构：回答、引用、开放问题、执行动作和拒答原因。
- 增加生成后引用完整性、引用存在性、关键约束和 Fake 来源校验；修复失败则拒答或转人工。

**验收标准**

- 所有企业事实引用率为 100%，不存在指向未授权或不存在证据的引用。
- 冲突证据不会被无提示地合并成确定结论。
- Fake Tool 结果不会被表达为真实业务事实。

### 5.10 SSE 不是真正的模型流式链路

**当前问题**

当前流式端点先等待完整 Agent 结果，再把答案字符串切片发送；它验证了 SSE 协议，但没有优化模型 TTFT，
也无法在生成过程中传播取消。

**根因**

- 阶段一优先统一了流事件契约和前端体验。
- GraphRAG、Agent 和持久化路径仍以完整 `ChatResult` 为主要返回值。

**解决方案**

- 定义内部版本化 Run Event Stream，覆盖 started、routing、retrieving、delta、citation、status、error、completed。
- 模型 Provider 的流式输出直接进入 Agent 事件流，禁止完成后伪流式切片。
- 客户端断开时传播取消；已经执行的 Tool 和消息状态仍需持久化为可解释终态。
- 流式与非流式必须共享同一最终结果归并器和审计，不维护两套业务逻辑。

**验收标准**

- 第一个 delta 在模型完整回答完成前产生。
- 事件序号单调、结束事件唯一，取消后不会继续无界生成或触发新的副作用。
- 流式与非流式最终答案、引用、状态和审计语义一致。

### 5.11 Supervisor 尚未形成多级路由和多 Agent 收敛

**当前问题**

当前规则路由安全、可预测，但没有完整的规则、Embedding、小模型、复杂模型级联；每次运行只选择一个专家后结束，
不存在单轮多 Agent 结果收敛和冲突仲裁。

**根因**

- 无真实数据时无法可靠训练或校准路由阈值。
- 阶段一刻意选择短图，避免自由 Agent 环路和工具误调用。

**解决方案**

- 保留规则优先和高风险 fail-safe；增加版本化 Router Port，使 Embedding/小模型分类可配置启用。
- 所有模型路由必须输出严格 Schema、置信度和候选意图，失败时回退规则或澄清。
- 阶段 1.5 只实现受控的复合意图计划与结果收敛接口，限制最大专家数量、步骤和总预算。
- 冲突仲裁优先使用数据时效、权威来源和确定性规则，不能只比较模型自报置信度。

**实现结果（2026-07-14）**

- `RouterPort` 已输出版本化候选、置信度、理由和最多两个专家的有界计划。
- `ResultConsolidatorPort` 与 `deterministic-consolidator-v1` 已固化最多两个专家的收敛契约；权威来源优先，
  同级且时间可比时取更新证据，同级冲突无法确定性裁决时强制澄清。
- 当前运行图仍保持单专家安全路径；收敛接口不触发未经真实评测的多专家执行，只减少阶段二领域契约改动。

**验收标准**

- 高风险低置信问题不会随机进入写 Agent。
- 复合意图执行有硬步骤上限并能终止。
- 每个 Handoff、候选意图、仲裁依据和降级均可审计。

### 5.12 Tool 契约执行仍需加固

**当前问题**

Tool 已有注册、输入字段检查、角色、风险、超时和审计，但输出 Schema 没有统一运行时验证，
Retry Policy 尚未形成可观测执行策略，也没有依赖级熔断和舱壁。

**根因**

- 阶段一 Tool 全部在进程内或 Fake，失败面较小。
- Registry 保存了治理元数据，但 Executor 尚未完整消费所有策略。

**解决方案**

- Tool 输入输出统一使用版本化 Pydantic Schema，不只依赖手写 JSON 字段检查。
- Retry 仅允许明确幂等操作，记录次数、退避和最终决策；写操作不能自动无限重试。
- 为不同依赖配置独立并发上限、超时预算和熔断状态，避免单个 Tool 拖垮聊天服务。
- Tool 结果进入上下文前执行脱敏、大小限制、来源标记和 Prompt Injection 数据域隔离。

**验收标准**

- 非法 Tool 输出不能进入 Agent State 或用户响应。
- 非幂等写操作自动重试次数为零。
- Tool 超时、熔断、降级和转人工路径均有确定错误码和测试。

### 5.13 安全防护仍以规则和测试为主

**当前问题**

项目已有权限 fail-closed、知识指令隔离、Tool 最小权限、日志脱敏和攻击样本，但缺少输入/输出统一安全判定接口、
字段级加密、密钥轮转接入和长期记忆隐私治理。

**根因**

- 阶段一没有真实敏感业务数据，避免引入外部收费 Guard 服务。
- 规则脱敏无法覆盖所有地址、自由文本和新型注入表达。

**解决方案**

- 定义 Input/Output Safety Port，CI 使用确定性 Fake/规则实现，真实 Guard 作为后续 Adapter。
- 对用户输入、检索证据、Tool 结果和模型输出分别标注信任域，禁止把外部文本提升为系统指令。
- 将长期记忆纳入数据分类、最小化、保留期、用户删除和访问审计。
- 保持生产 Secret/KMS 为阶段二部署能力，但阶段 1.5 完成配置 Port、轮转兼容和无明文测试。

**验收标准**

- Prompt Injection 不能改变租户、权限、Tool 风险和审批规则。
- 日志、Trace、Manifest 和错误响应中敏感原值泄露数量为零。
- 删除用户记忆后，MySQL、Redis 和派生索引均不可再检索到该项。

### 5.14 评测尚未覆盖记忆与可靠性

**当前问题**

现有合成 Golden Set 很好地覆盖路由、检索、引用、拒答和权限，但缺少长对话、摘要、并发、幂等、恢复和状态迁移评测。

**根因**

- 阶段一评测目标是证明 GraphRAG 主链路正确。
- 真实业务数据尚未到位，无法建立业务级自然分布。

**解决方案**

- 建立独立、版本化的 Memory & Reliability Golden Set，仍使用虚构数据。
- 按 4、8、12、16 轮组织多轮样本，包含指代、话题切换、否定约束、过期事实和冲突历史。
- 增加进程中断、Redis 丢失、并发重复请求、旧状态版本和 Tool 部分成功样本。
- 记录上下文策略、Prompt、模型、State 和评测集版本，形成可比较报告。

**最低指标**

| 指标 | 阶段 1.5 门槛 |
| --- | --- |
| 跨租户/跨用户记忆污染 | 0 |
| 关键结构化约束保留率 | 100% |
| 重复请求产生的重复消息/Tool 副作用 | 0 |
| Checkpoint 安全恢复用例通过率 | 100% |
| 状态迁移固定夹具通过率 | 100% |
| 需要企业证据的回答引用率 | 100% |
| 上下文超预算率 | 0 |
| 长会话任务成功率下降 | 相对短会话不超过 5 个百分点 |
| 重复追问已知关键字段率 | 不高于 5% |
| 约束违反率 | 安全/金额/权限约束为 0；普通业务约束低于 2% |

### 5.15 Prompt、模型与上下文策略缺少统一治理

**当前问题**

模型名和部分阈值已配置化，Embedding/抽取版本也被记录，但核心 Prompt 仍有代码内硬编码，
`prompt_version` 主要是固定字符串，无法证明某次回答使用了哪一份完整策略。

**根因**

- 阶段一 Prompt 数量有限，尚未出现多人或多版本运营需求。
- Prompt、上下文策略和模型路由没有共同的发布单元。

**解决方案**

- Prompt 移入版本化资源目录或 Prompt Registry，通过稳定 ID 和内容 hash 加载。
- 建立 Generation Manifest，绑定 Prompt、模型、Router、Embedding、Rerank、State 和 Context Policy 版本。
- 所有策略变更必须运行对应 Golden Set；失败时可回滚到上一稳定版本。
- 无真实流量前不做线上 A/B，但必须保证接口和审计字段可支持阶段二灰度。

**验收标准**

- 任一 Agent Run 都能定位完整版本组合。
- 修改 Prompt 或上下文策略会触发相关评测门禁。
- 回滚后无需修改领域模型和业务数据即可恢复上一稳定行为。

### 5.16 知识运营与生产性能仍未闭环

**当前问题**

解析、OCR、父子分块、三库写入、版本和下线已经完成，但缺少知识冲突、质量评分、审核发布、真实容量和延迟证据。

**根因**

- 当前没有实际业务知识和运营角色。
- CI 数据量小，无法代表生产规模和真实百炼延迟。

**解决方案**

- 阶段 1.5 增加重复、冲突、过期和低质量 Chunk 的检测报告接口，不自动删除业务内容。
- 为知识发布和下线保留审核状态，但真实组织审批留到阶段二。
- 建立可重复的合成容量测试和故障注入，测量上下文构造、检索、Rerank、流式 TTFT 和恢复耗时。
- 生产 GPU Rerank、KV Cache、集群扩容和冷热分层仍由实际负载决定，不在阶段 1.5 虚假实现。

**验收标准**

- 冲突、重复、过期和低质知识可被发现并定位到来源版本。
- 合成负载下没有无界队列、无限重试或内存持续增长。
- 性能报告明确区分 Fake/本地结果与真实模型、真实集群指标。

## 6. 阶段 1.5 实施顺序

### 里程碑 A：会话一致性基座

- 建立 `client_turn_id`、消息序号、Session revision 和同会话单运行策略。
- 调整消息与 Agent Run 的提交边界，使每轮状态可解释、可重试、可去重。
- 完成并发、重复请求、取消和宕机注入测试。

进入下一里程碑前必须证明：重复副作用为零，跨会话仍可并发，同一会话不存在静默覆盖。

### 里程碑 B：上下文与短期记忆

- 打通会话历史到 Agent、Query Rewrite 和检索。
- 实现 Context Assembler、Token 预算、滚动摘要、结构化 Conversation State 和 Manifest。
- 增加长会话、摘要失真、话题切换和约束保留评测。

进入下一里程碑前必须证明：上下文不超预算，硬约束不依赖自然语言摘要，历史不会跨用户污染。

### 里程碑 C：Checkpoint、状态迁移与审批恢复

- 定义安全节点、恢复语义、State Migration Registry 和 MySQL 最小安全快照。
- 完成 Fake 退款草单的真实 interrupt/callback/resume 演示，但不增加真实退款执行路径。
- 覆盖 Redis 丢失、旧版本、损坏状态和 Tool 已成功等恢复场景。

进入下一里程碑前必须证明：所有恢复路径幂等，未知状态 fail closed，恢复权限隔离正确。

### 里程碑 D：真实流式与执行可靠性

- 将 Provider 流式输出接入统一 Run Event Stream。
- 补齐 Tool 输出验证、受控重试、并发舱壁、取消和降级。
- 保证流式与非流式共享同一最终状态和审计。

进入下一里程碑前必须证明：首个 delta 在完整答案前产生，取消不会产生新副作用，错误终态唯一。

### 里程碑 E：记忆治理、安全与评测门禁

- 定义长期记忆 Schema、Port、禁用默认和用户治理接口。
- 完成输入/输出安全 Port、上下文信任域和删除传播测试。
- 将 Memory & Reliability Golden Set 加入 CI，绑定 Prompt/模型/策略版本。

阶段 1.5 只有在本文指标全部达标、文档与代码一致后才算完成。

## 7. 预期数据与接口调整

以下是实施方向，具体字段必须在编码前通过领域模型和 Alembic Migration 固化：

- `sessions`：增加单调 revision、最后消息序号、当前运行和上下文策略版本。
- `messages`：增加 `client_turn_id`、会话内 sequence、消息状态和输入 hash，并建立幂等唯一约束。
- `agent_runs`：增加输入/结果 hash、恢复来源、Checkpoint/State/Prompt/Context Policy 版本。
- Conversation State：保存结构化约束、摘要版本、覆盖消息范围和最后处理序号。
- Safe Resume Snapshot：保存可恢复节点、状态版本、已完成副作用摘要和下一合法动作。
- Long-term Memory：保存类型、值、来源、确认、敏感等级、有效期、版本和删除状态；阶段 1.5 默认禁止自动写入。
- Context Manifest：保存 Token 计数、被选消息/证据 ID、丢弃原因、版本组合和降级决策。

所有新增公共契约都必须版本化。数据库变化必须提供 Alembic Migration，不能只修改 ORM。

## 8. 明确不属于阶段 1.5 的事项

- 不接入真实退款、真实改地址、真实催单或其他业务写 API。
- 不部署生产 Kafka、Outbox Relay、DLQ 或拆分异步微服务。
- 不部署生产审批平台；只完成 Fake 中断与恢复语义。
- 不建设生产多租户管理、计费、配额控制台。
- 不承诺多活、跨地域容灾、生产集群 SLO 或真实容量指标。
- 不为了使用新技术而默认启用 HyDE、Multi-Query、长期向量记忆或自由多 Agent 对话。
- 不把模型推测、聊天摘要或 Redis 数据提升为业务真理源。

这些能力继续保留为阶段二或生产上线工作，阶段 1.5 只确保当前模块化单体和契约能够安全承接它们。

## 9. 阶段 1.5 完成定义

必须同时满足以下条件：

- 会话历史真实进入上下文链路，并通过多轮指代与话题切换测试。
- 上下文采用统一 Token 预算，所有超限和丢弃决策可解释。
- 自然语言摘要与结构化约束分离，安全和业务硬约束不丢失。
- 同一会话具备幂等、顺序和并发控制，不产生重复副作用。
