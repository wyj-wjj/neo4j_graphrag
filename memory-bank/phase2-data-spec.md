## 1. 决策摘要

阶段二在没有真实业务数据、真实外部 API 和真实审批组织的前提下，先建设一个完全虚构、可重复生成、
内部状态一致、带机器可验证真值的中文电商“业务数字孪生”。它用于验证数据契约、Agent、GraphRAG、
Kafka、审批、多租户、安全、故障恢复和容量，不用于宣称真实业务效果。

核心决策如下：

1. 先生成权威业务事实，再派生知识、对话、事件和评测标签；模型不得决定金额、权限、状态或标准答案。
2. 数据生成必须由固定配置和固定 Seed 驱动，相同生成器版本、配置与 Seed 产生相同内容和校验和。
3. 合成业务数据必须显式标记 `fake/synthetic`，不得与真实生产数据、真实用户或真实业务写操作混用。
4. MySQL 继续保存本项目知识、状态、权限和审计真理；订单、物流和退款动态事实只通过业务 Port/模拟外部
   服务实时读取，不进入 Milvus、Neo4j 或长期记忆。
5. 知识源文件必须经过正式上传、解析、分块和索引链路；禁止直接制造 Milvus 向量或 Neo4j 派生结果来
   绕过入库验证。
6. 自动生成的大规模数据属于合成 Fixture 或银标评测集；未经过独立人工审核的数据不得命名为生产 Gold Set。
7. 仓库只提交规范、Schema、场景配置、固定 Seed、生成器和小型 Fixture；大规模产物不提交 Git。
8. 合成数据可以证明工程行为和安全不变量，但不能校准真实流量分布、真实风控阈值或生产 SLO。

## 2. 目标与非目标

### 2.1 目标

- 在没有真实数据时为阶段二提供足够丰富的知识、业务、会话、事件、审批和故障样本。
- 为每个样本生成可追踪的场景 ID、事实来源、预期行为、允许副作用和禁止副作用。
- 支持 CI、小型开发、完整集成、容量压测、故障演练和安全红队等不同规模。
- 覆盖单租户到多租户、单轮到长会话、正常链路到乱序/重复/DLQ 的完整状态空间。
- 让其他开发者或 AI 能根据 Manifest 重建同一数据集，不依赖创建者机器上的隐藏状态。
- 当未来取得少量脱敏真实数据时，可以新增分布配置和评测集，而不推翻生成器领域模型。

### 2.2 非目标

- 不训练或微调基础大模型，不把数据量本身视为模型质量。
- 不伪造某个未来供应商的真实 API 契约、错误码或 SLA。
- 不生成可联系的手机号、邮箱、证件号、银行卡或真实地址。
- 不抓取网页、公开用户内容或第三方版权资料来填充规模。
- 不把订单状态、VIP、权限或退款事实写入 RAG 知识库或用户长期记忆。
- 不用合成负载单独决定是否拆微服务、生产集群规模或真实容量承诺。
- 不允许任何合成审批触发真实退款、改地址、催单、通知或资金动作。

## 3. 数据设计原则

### 3.1 事实优先，语言后置

生成顺序固定为：

```text
数据集配置与 Seed
  → 租户、身份、商品和业务规则
  → 订单、物流、退款、审批等权威状态
  → 知识文档与版本
  → 会话任务和用户表达变体
  → 事件流、故障计划与期望终态
  → 评测标签和独立不变量校验
  → 导出与 Manifest
```

语言模型只允许生成或改写不改变事实的表达变体。模型输出必须通过实体占位符、事实对齐和 Schema 校验；
CI 生成路径不得调用收费模型。任何语言增强失败都只能丢弃该变体，不能修改权威事实。

### 3.2 可重复性

- 根 Seed 按数据集版本固定；各领域使用稳定派生 Seed，新增物流场景不得改变已有订单样本。
- 时间从固定 UTC 基准时刻按场景偏移生成，不读取执行机器当前时间决定业务事实。
- 金额全部使用十进制定点数，币种默认 `CNY`，禁止用浮点数累计金额。
- 合成 ID 使用固定命名空间、固定时间序列和 Seed 生成 UUIDv7 兼容值或项目统一的确定性测试 ID。
- 排序必须显式指定稳定键，禁止依赖数据库默认顺序、集合顺序或 Python 随机 Hash。
- Manifest 分离确定性内容与运行元数据；生成时间不能使业务文件校验和发生变化。

### 3.3 真值与实现解耦

- 业务 Oracle 与被测应用使用独立规则实现，不直接调用生产应用函数计算期望值。
- 每条期望答案回溯到业务事实 ID、知识锚点或 Tool 响应，不从被测系统输出反推标签。
- 开发集、测试集和保留集按场景族拆分，不能只把同一模板的不同措辞随机分到两边。
- 保留集不可用于调 Prompt、阈值、路由或生成模板；只在发布评测时读取。
- 故意重复、冲突、过期和乱序的数据必须有原因标签；其他意外异常一律视为生成失败。

### 3.4 安全与隔离

- 每条顶层业务记录都有 `tenant_id`，或能通过不可变父实体唯一关联到租户。
- 每个导出记录携带或可关联 `dataset_id`、`dataset_version`、`scenario_id` 和 `is_synthetic=true`。
- 合成租户、数据库、Bucket、Collection、Topic 前缀和 Redis Namespace 必须带 `synthetic`、`test` 或
  数据集版本后缀。
- 清理工具只能删除本次 Manifest 明确列出的资源；拒绝通配删除和来源不明资源。
- 生成产物不得包含 `.env`、密钥、Token、真实连接串或可用默认密码。

## 4. 虚构业务世界

### 4.1 默认设定

| 项目 | `synthetic-commerce-v1` 默认值 |
| --- | --- |
| 行业 | 完全虚构的多租户中文电商客服 |
| 主要语言 | 简体中文；保留少量英文和中英混合表达 |
| 存储时区 | UTC |
| 默认展示时区 | `Asia/Shanghai` |
| 币种 | CNY |
| 渠道 | Web、App、模拟小程序、模拟客服工作台 |
| 租户显示名 | 仅使用“演示商城 A”“合成租户 B”等明确虚构名称 |
| 邮箱域名 | `.invalid` 保留域名 |
| 地址 | “测试省/演示市/样例区”等不存在的地址 |
| 联系字段 | 无效或遮罩占位值，不生成可联系个人信息 |

所有显示名称、政策、商品、机构和人物均为虚构。生成器不得从联系人、系统用户名、本地文件或网络内容中
提取名称。

### 4.2 身份和角色

最小角色集：

| 角色 | 可见范围 | 允许能力 |
| --- | --- | --- |
| `customer` | 本人订单、物流和公开知识 | 查询、发起草单、查看本人状态 |
| `customer_service` | 获授权队列和部门知识 | 查单、查物流、创建低风险草案、创建工单 |
| `supervisor` | 所属租户审批范围 | 审批、拒绝、查看受控审计摘要 |
| `knowledge_admin` | 所属租户知识库 | 上传、审核、发布、下线和质量报告 |
| `auditor` | 所属租户脱敏审计 | 只读审计，不查看非必要原文 |
| `tenant_admin` | 所属租户配置 | 用户、角色、配额和功能开关管理 |

每个角色都必须生成允许、明确拒绝、缺少策略和跨租户四类样本。Deny 优先，不允许管理员角色通过请求正文
自行声明。

### 4.3 租户等级

生成 Standard、Enterprise 和 Regulated 三类合成租户，用于测试不同配额、知识隔离和审批矩阵。等级只影响
确定性配置，不允许模型自行提高租户等级或额度。高安全租户可以在容量 Profile 中映射到独立 Collection、
Schema 或 Neo4j Database，但 `ci-small` 只验证逻辑隔离。

## 5. 业务领域与状态机

### 5.1 商品与库存

商品包含 Product、SKU、分类、价格、税率、售后类别和虚构品牌。库存只为订单状态和可售性提供事实，
不作为长期记忆。生成无库存、预售、虚拟商品、组合商品和不可退商品等边界样本。

### 5.2 订单

订单主状态采用受控状态机：

```text
created → paid → allocated → shipped → delivered → closed
    └──────────────→ cancelled
paid/allocated → refund_pending → refunded
```

生成器必须阻止非法跳转，并覆盖：

- 未支付取消、支付后取消失败、部分发货、多包裹、部分签收。
- 优惠、运费、税费、部分退款和不可退明细。
- 订单归属错误、租户错误、订单不存在和已归档。
- 未出库可改地址、已出库不可直接改地址、高价值订单需审批。

订单金额不变量：订单应付金额等于明细小计减优惠加运费和税费；所有退款累计不得超过可退金额。

### 5.3 物流

物流状态至少覆盖 `label_created`、`picked_up`、`in_transit`、`exception`、`out_for_delivery`、
`delivered` 和 `returned`。Tracking Event 的时间必须单调，发货前不能出现物流揽收，签收不能早于出库。

异常场景包括长时间无更新、错误分拨、拒收、丢件、退回、重复催单、催单频控和供应商超时。

### 5.4 退款

退款流程在合成外部业务系统中分为：

```text
calculate → create_draft → risk_check → approval_pending
  → approved | rejected | expired
  → synthetic_execute → reconciled | compensation_required
```

`synthetic_execute` 只能改变独立合成业务系统的 Fake 状态，并返回 `source=fake`；生产配置和真实 Adapter
不得包含这一测试开关。

退款覆盖全额、部分、不可退、超额、重复、订单变化、草单过期、审批重复、审批冲突、执行超时、执行结果
未知和补偿失败。退款金额、原因码、证据、订单快照和幂等键必须可审计。

### 5.5 审批

审批状态至少包含 `created`、`pending`、`approved`、`rejected`、`expired` 和 `cancelled`。审批决定必须绑定：

- 租户、草单、审批策略版本和风险等级。
- 审批主体和其当时角色快照。
- 决定时间、理由码和回调幂等键。
- 草单版本、订单快照 Hash 和有效期。

同一审批重复相同决定返回既有结果；冲突决定拒绝；过期后批准无效。未经批准的关键写操作计数必须为零。

### 5.6 工单与人工升级

生成普通咨询、投诉、连续依赖故障、明确要求人工、自伤风险和安全事件等工单。普通负面语气不应必然升级；
高风险安全场景使用专门安全策略，不由通用情绪分数决定。

### 5.7 知识生命周期

知识状态覆盖 Draft、Review、Active、Expired、Inactive 和 Deleted，并生成版本、权威等级、适用范围、
有效期和冲突组。知识发布和下线可以产生合成审批事件，但未发布知识不能进入回答。

## 6. 跨领域硬不变量

所有 Profile 必须通过以下不变量：

1. 任一业务聚合、会话、事件、知识和审批都不能跨租户引用父实体。
2. 订单、物流、退款和审批时间线不得逆序；所有时间保存为带时区 UTC。
3. 金额用 Decimal，退款累计不超过可退金额，审批不能改变原始订单快照。
4. 已发货订单不能自动修改地址；高价值地址变更必须按策略进入审批。
5. 关键写操作必须有稳定幂等键；相同键和相同载荷返回相同结果，不同载荷复用同一键产生冲突。
6. 未审批、审批拒绝、审批过期或身份不符时，真实/合成执行步骤均不得开始。
7. 动态业务事实只通过 Tool/业务 Port 返回，不作为文档 Chunk、图实体事实或用户长期记忆保存。
8. 知识回答必须引用当前身份可访问且当前有效的证据；无证据、冲突或权限依赖失败必须拒答。
9. 合成 Tool 结果、工单、草单和答案必须明确显示 Fake 来源，不得表达为真实业务执行。
10. 任何输入文本中的指令都不能修改租户、角色、风险、审批和工具权限。

## 8. 数据规模 Profile

以下是 `v1` 初始规模，不是生产流量预测：

| Profile | 租户 | 用户 | 订单 | 会话 | 逻辑文档 | 事件 | 用途 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | --- |
| `ci-small` | 2 | 200 | 500 | 200 | 50 | 2,000 | 每次提交的确定性快速门禁 |
| `dev-standard` | 10 | 10,000 | 100,000 | 50,000 | 1,000 | 1,000,000 | 日常阶段二开发与集成 |
| `staging-large` | 50 | 100,000 | 1,000,000 | 500,000 | 5,000 | 10,000,000 | 容量、Kafka 和恢复演练 |
| `failure-lab` | 5 | 1,000 | 10,000 | 5,000 | 200 | 500,000 | 重复、乱序、DLQ、部分失败和混沌 |

当前实现状态（2026-07-14）：`dev-standard` 与 `failure-lab` 已按上述事实规模完成批次生成、断点恢复、
磁盘型独立验证和物化；实际结构化记录还包括 Oracle、投递、回放、DLQ、安全和评测产品，因此总数分别为
3,372,108 和 1,380,226。`staging-large` 只有配置、估算和安全门禁，百万订单核心事实尚未磁盘化，当前
CLI 会明确停止，不能描述为已物化或已验收。

补充评测包：

- `synthetic-gate-v2`：至少 2,000 条机器真值完整的银标门禁样本。
- `security-v2`：至少 5,000 条越权、注入、敏感信息、伪引用和危险操作样本。
- `memory-v2`：至少 500 条 4/8/12/16/32 轮会话与恢复样本。
- `golden-v2`：初始目标 300 条经过独立人工复核的样本；人工复核完成前只能标记为 candidate。

物理复杂文件不按逻辑文档一比一生成。`dev-standard` 至少生成 200 个混合格式文件，`staging-large` 至少
生成 500 个；其余逻辑文档使用 Markdown/HTML，以控制磁盘和解析成本。每种支持格式必须覆盖正常、边界和
损坏样本。

## 9. 默认分布

### 9.1 会话意图分布

| 类型 | 初始比例 |
| --- | ---: |
| FAQ | 20% |
| KB/政策知识 | 25% |
| 订单 | 15% |
| 物流 | 15% |
| 退款/售后 | 10% |
| 投诉与人工升级 | 5% |
| 多意图、含糊和需要澄清 | 10% |

至少 25% 会话为多轮；长会话固定覆盖 4、8、12、16 和 32 轮。普通 Profile 不混入依赖故障以伪装自然
分布；故障率由独立 `failure-lab` 配置控制。

### 9.2 语言变体

- 规范中文、口语、省略、错别字、标点缺失、中英混合和编号查询。
- 指代、话题切换、条件补充、否定、反悔和重复追问。
- 同一事实的表达变体不能改变实体、金额、时间、权限和动作风险。
- 语言去重以模板族和语义标签共同控制，不能仅按字符串 Hash 去重。

### 9.3 知识质量分布

普通开发数据以有效知识为主；过期、重复、冲突、低质量和越权知识必须显式按场景注入。其比例存放在
Profile 配置中而非代码常量。初始 `dev-standard` 可采用 Active 70%、历史/过期 10%、重复 7%、冲突 5%、
低质量 5%、未发布/下线 3% 的可比较基线；这些比例不是生产估计。

## 10. 知识源与证据真值

### 10.1 内容范围

知识库覆盖商品、发票、会员、物流、退换货、售后、隐私、渠道、地区、时间和权限政策。文档必须包含：

- 单事实、跨章节和 1～2 跳实体关系。
- 表格、列表、标题层级、扫描图片和混合排版。
- 同主题不同版本、有效期切换和适用范围。
- 精确编号、专有虚构名词、别名和同名实体。
- 明确无答案、冲突、过期、未发布和越权样本。
- 文档内 Prompt Injection、伪系统指令和伪 Tool 请求。

### 10.2 证据锚点

生成器在源文档中创建稳定 `evidence_anchor_id`，表示可验证的事实单元。由于正式入库会产生实际
`document_id`、`version_id` 和 `chunk_id`，评测不能在入库前猜测随机 Chunk ID。入库完成后由锚点解析器
根据内容 Hash、版本和来源位置生成 Anchor → Chunk 映射 Manifest。

解析规则：

- 一个 Anchor 可以映射一个或多个合法 Chunk，但必须有唯一权威源和适用范围。
- Anchor 无法解析、解析到错误租户或解析到无关版本时，数据集构建失败。
- Golden/Evaluation Case 保存 Anchor 和解析后的 Chunk ID；运行时指标使用实际 Chunk ID。
- 分块策略变化后必须重建映射和评测快照，不能沿用旧 Chunk 期望值。

### 10.3 入库边界

- 先创建原始文件，再调用现有上传 API 和入库任务处理器。
- MySQL 生成 Chunk、ACL、版本和状态；Milvus/Neo4j 只由正式 Handler 或未来 Kafka Worker 派生。
- 禁止生成器直接向 Milvus 写向量、向 Neo4j 写最终图或直接把 Chunk 标记完成。
- 对纯容量测试可生成预先计算的固定测试向量，但必须使用独立 Collection，并明确标记不参与质量评测。

## 11. 业务 API 模拟器数据

在没有真实 API 时，阶段二建立独立的合成业务系统模拟器。它实现现有 Order、Logistics、Refund 和 Approval
Port 对应的 HTTP 契约，但不属于 Agent 进程，也不允许 Agent 访问其数据库。

模拟器要求：

- 自己的合成业务存储是订单/物流/退款领域的权威来源，应用只能通过版本化 API/Port 查询。
- 所有响应包含 `source=fake`、`scenario_id`、`trace_id` 和稳定业务错误码。
- 支持成功、不存在、无权限、业务拒绝、429、超时、5xx、连接中断和结果未知。
- 写请求强制幂等；重复相同请求回放结果，冲突载荷返回稳定冲突错误。
- 故障场景由测试编排器或服务端场景配置选择，不能由普通用户请求头在生产模式触发。
- 动态业务事实不会复制到 RAG；对话需要时每轮重新调用 Tool 并重新鉴权。

未来接入真实供应商时，模拟器契约只能作为本项目预期契约，由真实 Adapter 完成字段和错误映射；不得声称
模拟器已经代表供应商实际行为。

## 12. 会话与评测标签

每个 Evaluation Case 至少包含：

- `case_id`、`scenario_id`、数据集/Schema/规则版本和 split。
- 租户、用户、角色、部门、渠道和允许数据范围。
- 单轮问题或完整有序对话，以及结构化硬约束。
- 预期意图、候选意图、Agent 或最多两个专家的受控计划。
- 允许 Tool 集、预期 Tool 顺序、输入事实引用和稳定幂等语义。
- 预期 Evidence Anchor、实体路径、文档版本、可回答性和引用要求。
- 预期答案状态：answered、refused、clarification、escalated 或 fake_result。
- 预期拒答原因、开放问题、审批状态和恢复来源。
- 允许副作用和禁止副作用；高风险默认禁止。
- 难度、语言、时效、权限、多跳、故障、安全和长会话标签。

答案文本不要求逐字匹配；企业事实、引用、约束、状态和副作用必须结构化判定。需要模型质量评分的案例与
确定性业务正确性分开报告。

## 13. 数据集分层与防泄漏

### 13.1 数据质量层级

| 层级 | 定义 | 可用于 |
| --- | --- | --- |
| Fixture | 小型手写或固定生成样本 | 单元、契约、CI |
| Synthetic Bronze | Schema 合法的大规模生成数据 | 容量和管道测试 |
| Synthetic Silver | 通过 Oracle、不变量、隔离和重放验证 | 离线工程门禁 |
| Golden Candidate | 自动标签并经抽样复核 | 预发布比较，不作为最终生产结论 |
| Golden | 独立人工复核且有版本/审核记录 | 发布质量门禁 |
| Real Calibrated | 合法脱敏的真实分布样本 | 生产阈值、SLO 和业务验收 |

### 13.2 Split 规则

- 按场景族、文档版本族、订单时间窗口和语言模板族划分 Dev/Test/Holdout。
- 同一订单、同一会话、同一文档近重复版本不能跨 Split。
- 安全攻击模板按攻击家族隔离，Holdout 保留未用于规则开发的变体。
- Holdout 的标签可在运行时读取用于评分，但不得进入 Agent Prompt、检索库或调参输入。
- 任何更改 Split 或标签的行为都会生成新数据集版本，不能静默覆盖报告。

## 14. Kafka、乱序与重放数据

事件使用现有版本化 Envelope，覆盖 `knowledge.events`、`agent.events`、`action.events` 和 `eval.events`。
正常事件流由事实状态变化派生；故障包再产生以下受控变体：

- 相同 `event_id` 重复投递。
- 相同聚合不同版本乱序到达。
- 不同消费者独立成功或失败。
- 暂时错误重试、永久错误和最大重试后进入 DLQ。
- Schema 未知版本、缺少租户、Hash 不匹配和无法反序列化。
- Relay 在发布前、发布后和标记完成前中断。
- Consumer 在外部副作用成功后、Inbox 提交前中断。
- DLQ 修复后重放和整租户索引重建。

事件重放验收不是“消息全部成功”，而是重放后的 MySQL 事实、Milvus/Neo4j 派生状态、Inbox 和审计记录与
Oracle 终态一致，并且不存在重复副作用。

## 15. 安全、隐私与虚假数据标识

### 15.1 禁止内容

- 真实姓名、真实公司内部文档、真实用户对话和真实地址。
- 可用手机号、邮箱、证件号码、银行卡号和第三方账号。
- API Key、Token、Cookie、私钥、数据库密码和真实连接字符串。
- 未经许可的网页抓取内容或第三方版权文档。

### 15.2 安全测试占位值

需要测试脱敏时使用明显无效的 Canary，例如全零数字、`.invalid` 邮箱和 `CANARY_SECRET_VALUE`，并在
Manifest 中列出。Canary 不得满足真实支付、登录、通信或云服务凭据格式。密钥扫描仍必须通过，不能通过
白名单掩盖真正泄露。

### 15.3 强制标识

- UI、API、Tool、事件和导出结果的 Fake 数据必须显示 `source=fake` 或 `is_synthetic=true`。
- 生产配置拒绝加载合成业务 Adapter、合成审批执行和故障注入控制面。
- 合成租户 ID 使用保留前缀，真实租户注册入口拒绝该前缀。
- 日志和报告标题明确写明 `synthetic`，不得把本地延迟或正确率描述为生产 SLO。

## 16. 生成器和数据验收门槛

每次生成至少执行以下门禁：

| 指标 | 门槛 |
| --- | ---: |
| Schema 合法率 | 100% |
| 主外键与跨领域引用完整率 | 100% |
| 金额与时间状态机不变量通过率 | 100% |
| 跨租户引用或可见性污染 | 0 |
| 未审批关键写操作 | 0 |
| 未标记 Fake 的业务结果 | 0 |
| 意外孤儿记录 | 0 |
| Event 重放终态一致率 | 100% |
| Evaluation Case 必填标签完整率 | 100% |
| Dev/Test/Holdout 近重复或实体泄漏 | 0 |
| 真实 PII、凭据和可联系信息 | 0 |
| 相同输入 Manifest 的业务文件校验和差异 | 0 |

此外必须：

- 随机抽样反查订单金额、时间线、权限、知识 Anchor 和会话真值。
- 对所有故意冲突/重复/过期样本核对其原因标签。
- 从空环境生成两次并比较确定性文件校验和。
- 在目标 Profile 上记录生成耗时、峰值内存、磁盘和文件数量，但不把它当生产服务性能。
- 执行密钥扫描、Schema 验证、关系不变量、权限矩阵和事件重放验证。

## 17. 资源命名、存储与清理

- 数据集 ID 格式为 `{domain}-{major_version}-{profile}-{seed_id}`。
- MySQL 测试数据库、Bucket、Collection、Neo4j 合成命名空间和 Kafka Topic 必须携带数据集 ID 或
  `synthetic/test` 前缀。
- Milvus 质量评测与容量测试使用不同 Collection，禁止向现有来源不明 Collection 写入。
- Neo4j Community 单数据库环境通过明确数据集和租户标签隔离；清理前必须按 Manifest 列出预计数量。
- Redis Key 使用独立数据集 Namespace 和短 TTL；Checkpoint 与容量缓存不可误用同一清理模式。
- 大文件生成采用流式批次，避免把百万级记录一次性加载进内存。
- 清理操作默认 dry-run，只能删除 Manifest 所有、数量匹配且名称满足安全前缀的资源。
- 任何数量、租户或版本不匹配都必须停止清理并报告，不得强制继续。

## 18. 版本与 Manifest

Manifest 至少记录：

- 数据规范、生成器、Schema、业务规则、语言模板和 Oracle 版本。
- 根 Seed 与各领域派生 Seed 标识。
- Profile、数量、分布配置和故障配置 Hash。
- 每个导出文件的相对路径、记录数、大小和 SHA-256。
- 知识文件、Anchor Map、Evaluation Split 和事件范围。
- 兼容的应用 Schema、Event、Tool、Agent State、Prompt 和 Context Policy 版本。
- 生成状态、验证报告路径和失败原因。
- 非确定性的运行元数据单独保存，不参与业务数据内容 Hash。

业务规则、Schema 或标签语义发生破坏性变化时升级数据集主版本；只增加兼容场景时升级次版本。已经用于报告的
数据集不可原地修改，修复错误也必须产生新版本并记录替代关系。

## 19. 未来实施顺序

本文通过后，阶段二数据工程按以下顺序另建实施计划；本节不代表已经实现：

1. 固化数据 Manifest、Profile、合成 ID、时间和金额的最小 Schema。
2. 实现独立业务事实引擎和不变量 Oracle，先产出 `ci-small`。
3. 实现知识政策、Evidence Anchor 和正式入库后的 Anchor Map。
4. 实现订单、物流、退款和审批模拟外部服务及契约测试数据。
5. 实现会话、语言变体、评测标签、安全样本和 Split 防泄漏检查。
6. 实现 Kafka 事件、故障计划、DLQ、重放和终态对账数据。
7. 扩展 `dev-standard`，完成可重复性、隔离、资源和全链路验收。
8. 最后生成 `staging-large`；只有实际需要压测时才物化，默认不随开发环境启动。
9. 独立复核 Golden Candidate，人工确认后再发布 `golden-v2`。

每一步都必须先验证小 Profile，再扩大规模。失败时保留 Manifest 和脱敏诊断，不保留不可解释的半成品为
“有效数据”。

## 20. 阶段二启用决策门

### 20.1 可以由合成数据解锁

- Kafka/Outbox Relay、消费者幂等、Inbox、DLQ 和重放。
- S3/MinIO/OSS Adapter 契约、对象生命周期和一致性检查。
- 订单、物流、退款、审批 Port 的 HTTP Adapter 与故障语义。
- 多租户逻辑隔离、配额、成本归因和安全门禁。
- 受控最多双专家执行、冲突收敛和故障恢复的工程验证。
- 百万级数据的本地/预发容量趋势和资源瓶颈定位。

### 20.2 不能只靠合成数据解锁

- 真实退款、真实改地址、真实催单或其他真实副作用。
- 真实供应商 API 的最终字段映射、错误码、SLA 和对账规则。
- 生产审批矩阵、金额阈值、风控规则和审批组织关系。
- 模型路由、Retrieval Rewrite、HyDE、Dynamic Top-K 的生产默认阈值。
- 长期记忆自动提取、个性化和真实用户同意策略。
- 生产 SLO、集群容量、成本预算和微服务拆分结论。

未来获得真实数据时，优先增加合法脱敏的 Real Calibrated 评测层，不覆盖合成集。真实数据必须经过授权、
最小化、脱敏、保留期和删除审查后才能进入独立受控环境。

## 21. 完成定义

本文档阶段的完成条件：

- 合成业务世界、状态机、数据产品、规模、真值、隐私和验收边界均明确。
- 明确区分 Fixture、Bronze、Silver、Golden Candidate、Golden 和 Real Calibrated。
- 不把动态业务事实写入 RAG 或长期记忆，不绕过正式入库链路生成派生索引。
- 大规模数据的存储、命名、Manifest、清理和 Git 边界明确。
- 对没有真实数据仍不能解决的问题作出明确限制，不承诺虚假生产效果。
- 后续 AI 开发者可以据此编写逐步实施计划，而无需猜测数据域、默认规模或安全边界。
