# 阶段一实施计划

## 1. 使用说明

本计划供 AI 开发者逐步实施阶段一 MVP。执行前必须完整阅读同目录下的 `architecture.md`、`phase1_env_checklist.md` 和 `tech-stack.md`，并遵守仓库根目录的 `AGENTS.md`。`phase1_env_checklist.md` 即本项目的权威设计文档，不得另建或假设存在 `design-document.md`。

执行规则：

- 严格按编号顺序推进，除非依赖关系已经通过测试证明不受影响。
- 一个步骤只完成该步骤描述的事项，不顺带扩展其他功能。
- 每一步开始前检查现有改动，避免覆盖用户或其他开发者的工作。
- 每一步完成后立即执行该步骤指定的测试。
- 只有达到“通过标准”后，才能在 `progress.md` 中记录完成并进入下一步。
- 测试失败时先记录失败现象和原因，再修复当前步骤；不得跳过测试。
- 每个里程碑完成后，运行该里程碑全部测试，并更新 `architecture.md`。
- 任何真实密钥、密码、用户数据和敏感对话都不得写入仓库、测试数据、日志或 Trace。
- 本计划只描述实施指令，不提供实现代码。具体实现必须遵守 `tech-stack.md` 的版本和边界。

## 2. 里程碑零：项目约束与可追踪基线

### 步骤 0.1：核对必读文档

- 指令：完整阅读 `AGENTS.md`、`memory-bank/phase1_env_checklist.md`、`memory-bank/tech-stack.md` 和 `memory-bank/architecture.md`，整理阶段一范围、禁止事项和阶段二预留点。
- 验证测试：逐项检查阶段一功能清单、阶段一不做事项、技术版本和安全要求是否均能在阅读记录中找到对应来源。
- 通过标准：没有未解释的范围冲突；如存在冲突，已在 `progress.md` 记录并暂停实施等待确认。

### 步骤 0.2：检查仓库与敏感信息状态

- 指令：检查仓库文件、忽略规则和版本历史中是否存在 `.env`、API Key、密码、Token 或真实业务数据；只记录风险，不传播敏感值。
- 验证测试：运行密钥扫描并人工检查环境文件、部署文件和 Markdown 文档中的凭据模式。
- 通过标准：仓库中不存在可用凭据；发现的凭据已被移除或标记为需要立即轮换，且 `.env` 已被忽略。

### 步骤 0.3：冻结阶段一验收范围

- 指令：把阶段一必须完成的能力、Fake 能力和明确推迟的能力与 `phase1_env_checklist.md` 中的权威范围逐项核对；发现差异时只更新该文件中的范围和验收基线，不创建第二份设计文档。
- 验证测试：将验收清单逐项与 `phase1_env_checklist.md` 对照，确认 Supervisor、KB、FAQ、Escalation 为真实能力，Order、Logistics、Refund 为契约加 Fake。
- 通过标准：每项能力只有一个明确阶段归属，不存在同一功能同时被标记为“阶段一完成”和“阶段二再做”。

### 步骤 0.4：建立步骤进度格式

- 指令：在 `progress.md` 中定义步骤编号、状态、完成日期、修改文件、测试结果、遗留问题和下一步字段。
- 验证测试：用步骤 0.1 创建一条示例完成记录，并检查能否从记录定位到对应测试结论。
- 通过标准：任何开发者仅阅读 `progress.md` 就能知道当前完成位置、验证结果和阻塞项。

### 步骤 0.5：建立初始架构清单

- 指令：在 `architecture.md` 中记录当前已有文件和目录的用途、尚未创建的计划模块以及外部依赖边界。
- 验证测试：逐个检查仓库根目录和 `memory-bank` 中的文件是否都在架构清单中有用途说明。
- 通过标准：不存在用途不明的项目文件；计划模块明确标记为“尚未实现”，不与现状混淆。

## 3. 里程碑一：工程骨架与可重复环境

### 步骤 1.1：创建后端模块目录

- 指令：按 API、应用、领域、Agent、检索、入库、Tool、基础设施和可观测性边界创建 Python 包目录，只添加最小包标识和职责说明。
- 验证测试：让 Python 解释器发现所有顶层包，并检查领域层没有导入基础设施模块。
- 通过标准：所有模块可被发现，依赖方向符合 `AGENTS.md`，且没有循环导入。

### 步骤 1.2：建立 Python 项目元数据

- 指令：创建 `pyproject.toml`，锁定 Python 3.12 范围，按运行、开发和测试依赖组声明 `tech-stack.md` 规定的直接依赖。
- 验证测试：在全新虚拟环境中解析项目依赖，并检查 Python 3.11 和 3.13 会被运行时范围拒绝。
- 通过标准：依赖解析成功，直接依赖无重复或互相冲突，运行时范围正确。

### 步骤 1.3：生成并固定 Python 锁文件

- 指令：使用 uv 生成锁文件并提交，禁止手工修改锁文件。
- 验证测试：删除本地虚拟环境后使用冻结模式重新安装，比较两次解析出的包版本。
- 通过标准：两次安装版本完全一致，冻结安装不触发锁文件变更。

### 步骤 1.4：配置代码质量工具

- 指令：在项目元数据中配置 Ruff、mypy 和 pytest，统一目标 Python 版本、源码目录、测试目录和严格程度。
- 验证测试：分别运行格式检查、静态检查和空测试收集，确认工具都能启动且读取同一项目配置。
- 通过标准：三个工具均正常退出，没有找不到源码或配置冲突。

### 步骤 1.5：创建最小应用工厂

- 指令：建立 FastAPI 应用工厂，只注册应用元数据、版本前缀和生命周期入口，不接入业务功能。
- 验证测试：使用测试客户端创建应用两次，检查实例相互独立且 OpenAPI 文档可生成。
- 通过标准：应用可重复创建，OpenAPI 生成成功，没有模块导入副作用。

### 步骤 1.6：建立配置模型

- 指令：使用 Pydantic Settings 定义应用、MySQL、Redis、Milvus、Neo4j、百炼、Langfuse、上传和检索配置，区分必填项与安全默认值。
- 验证测试：分别使用完整配置、缺少必填配置、非法端口、非法阈值和生产环境启用 Fake 的配置启动设置加载。
- 通过标准：完整配置通过；所有危险或非法配置在应用启动前被明确拒绝。

### 步骤 1.7：建立环境变量示例

- 指令：创建 `.env.example`，列出所有配置项、非敏感示例和用途说明，不包含真实凭据。
- 验证测试：用 `.env.example` 的非敏感本地值加载配置，并运行密钥扫描。
- 通过标准：开发配置可加载，密钥扫描没有发现可用凭据，生产必填密钥没有危险默认值。

### 步骤 1.8：建立结构化日志和请求标识

- 指令：配置结构化 JSON 日志，为每个请求生成或接收 `request_id`，并将其传入应用上下文。
- 验证测试：发起两个独立请求和一个携带合法请求标识的请求，检查日志中的标识生成与透传行为。
- 通过标准：独立请求标识不同，合法外部标识被安全透传，日志不含请求正文和密钥。

### 步骤 1.9：建立本地依赖编排文件

- 指令：根据 `tech-stack.md` 为 Redis 8.2、Neo4j 5.26 LTS、Milvus 2.6.14及其内部依赖创建 Docker Compose；MySQL 提供可选 Profile。
- 验证测试：验证 Compose 配置语法，检查镜像版本、持久化卷、健康检查、端口和非默认凭据要求。
- 通过标准：配置可解析，默认不会启动阶段二组件，所有核心依赖都有健康检查。

### 步骤 1.10：建立基础健康检查

- 指令：提供 liveness 和 readiness 两类端点；readiness 分别报告 MySQL、Redis、Milvus、Neo4j 和模型配置状态。
- 验证测试：在全部依赖可用、单个依赖不可用和多个依赖不可用三种情况下请求健康端点。
- 通过标准：liveness 只反映进程存活；readiness 准确指出失败依赖且不泄露连接字符串或密码。

### 步骤 1.11：建立基础 CI 门禁

- 指令：在 GitHub Actions 中建立冻结依赖安装、格式检查、静态检查、单元测试和密钥扫描的基础工作流，外部数据库和收费模型暂用 Fake。
- 验证测试：分别提交格式错误、类型错误、失败单元测试、测试密钥样本和正常变更，检查对应 Job 的结果。
- 通过标准：四类错误均在对应门禁失败，正常变更通过，工作流不访问收费模型或真实业务数据。

### 里程碑一验证

- 指令：在干净环境完成冻结安装、质量检查、应用启动和依赖健康检查，并更新 `architecture.md` 的工程结构部分。
- 验证测试：由未参与实现的开发者仅根据仓库文档重复安装和启动流程。
- 通过标准：新环境可复现，所有里程碑一步骤测试通过，架构文档反映当前文件结构。

## 4. 里程碑二：领域模型与稳定契约

### 步骤 2.1：定义通用标识和时间规则

- 指令：定义租户、用户、会话、运行、文档、Chunk、事件和 Tool 调用的标识类型，以及 UTC 时间和版本字段规则。
- 验证测试：构造有效、空值、格式错误和跨类型误用的标识输入，检查验证结果。
- 通过标准：有效标识可序列化，非法值被拒绝，不同领域标识不会被静默混用。

### 步骤 2.2：定义统一错误模型

- 指令：定义配置、鉴权、验证、依赖、超时、冲突、未找到和内部错误类别，并为对外错误分配稳定错误码。
- 验证测试：将每类领域异常映射成 API 错误，检查状态、错误码、请求标识和用户可读信息。
- 通过标准：映射完整且稳定，响应不包含内部堆栈、数据库语句或敏感参数。

### 步骤 2.3：定义知识与存储 Port

- 指令：定义知识仓库、向量存储、图存储、Checkpoint、对象存储和授权 Port，明确输入、输出、超时语义和资源关闭责任。
- 验证测试：为每个 Port 建立最小 Fake 实现并运行契约测试，确认调用方不依赖具体数据库类型。
- 通过标准：Fake 实现可替换真实实现，领域层没有第三方数据库 SDK 类型。

### 步骤 2.4：定义模型能力 Port

- 指令：定义聊天模型、Embedding、实体抽取和 Reranker Port，明确批量、流式、结构化输出、模型版本和用量元数据。
- 验证测试：使用固定 Fake 响应验证同步结果、流式片段、结构化失败和超时行为。
- 通过标准：调用方能用同一契约切换百炼和 Fake，错误语义一致。

### 步骤 2.5：定义阶段二业务服务 Port

- 指令：定义订单、物流、退款和审批 Port，划分只读、低风险写入和关键写入，并要求写操作携带幂等键。
- 验证测试：使用 Fake Adapter 验证成功、业务拒绝、重复请求、超时和无权限场景。
- 通过标准：所有业务服务可在不修改 Agent 的情况下替换 Adapter，关键写操作不能绕过幂等和审批字段。

### 步骤 2.6：定义版本化 Tool 契约

- 指令：为阶段一全部 Tool 定义全局唯一名称、版本、输入、输出、风险级别、权限、超时、重试和审计策略。
- 验证测试：对每个 Tool 执行有效输入、缺字段、额外字段、错误枚举和危险参数测试。
- 通过标准：非法输入在调用业务服务前被拒绝，Tool 名称和版本不重复。

### 步骤 2.7：定义事件 Envelope

- 指令：定义阶段一 Outbox 与阶段二 Kafka 共用的事件 Envelope，包含事件标识、类型、版本、租户、聚合标识、时间、Trace 和载荷摘要。
- 验证测试：序列化并反序列化每种计划事件，测试未知版本、缺少租户和重复事件标识。
- 通过标准：合法事件往返一致，非法事件被拒绝，事件契约不依赖 Kafka 客户端类型。

### 步骤 2.8：定义 Agent State

- 指令：定义输入、编排、检索、工具、审批和输出状态字段，明确字段所有者、合并方式、默认值和状态版本。
- 验证测试：测试状态创建、节点局部更新、列表累加、非法覆盖、序列化和旧版本拒绝或迁移。
- 通过标准：状态可持久化和恢复，不同节点不能意外清除其他节点数据。

### 步骤 2.9：定义身份与授权上下文

- 指令：定义租户、用户、角色、身份来源和授权声明的稳定模型及验证 Port；阶段一只启用 `default` 租户，但所有调用链必须显式携带授权上下文。
- 验证测试：构造合法本地测试身份、缺少租户、缺少角色、伪造角色、跨租户和生产环境测试身份场景。
- 通过标准：合法身份可传入应用服务；非法、伪造、跨租户和生产测试身份在进入数据库、检索或 Tool 前被拒绝。

### 里程碑二验证

- 指令：运行所有契约测试和类型检查，并在 `architecture.md` 记录 Port、Adapter、Agent State 和事件边界。
- 验证测试：用 Fake 替换全部外部依赖，完成一次不访问网络和数据库的契约级流程。
- 通过标准：流程通过，领域与应用层不依赖具体基础设施 SDK。

## 5. 里程碑三：MySQL 真理源

### 步骤 3.1：建立异步数据库生命周期

- 指令：配置 SQLAlchemy 异步 Engine、Session 工厂、连接池、事务辅助和应用关闭清理。
- 验证测试：并发创建多个短事务，测试提交、回滚、连接失败和应用关闭后的连接释放。
- 通过标准：事务隔离明确，异常会回滚，关闭后没有连接泄漏。

### 步骤 3.2：建立文档与版本模型

- 指令：建立文档、文档版本和入库任务表，包含租户、状态、对象 Key、hash、MIME、大小、有效期和审计时间。
- 验证测试：测试同租户重复 hash、跨租户相同文件、版本递增、状态约束和非法时间范围。
- 通过标准：唯一约束和状态约束符合设计，跨租户数据相互独立。

### 步骤 3.3：建立 Chunk 与索引状态模型

- 指令：建立 Chunk、父子关系和索引状态表，记录原文、标题路径、页码、content hash、Embedding 版本、向量状态和图状态。
- 验证测试：测试父子关联、重复 Chunk、不同版本 Chunk、索引部分成功和失败原因保存。
- 通过标准：可以准确查询每个 Chunk 的来源、版本和两类派生索引状态。

### 步骤 3.4：建立 ACL 模型

- 指令：建立 Chunk ACL 与策略关联，支持租户、角色、部门、状态和有效期的阶段一最小权限模型。
- 验证测试：构造允许、拒绝、过期、下线、跨租户和无策略场景并查询权限结果。
- 通过标准：只有明确允许且有效的数据可返回；缺少权限上下文时默认拒绝。

### 步骤 3.5：建立会话与 Agent 审计模型

- 指令：建立会话、消息、Agent Run、Agent Step 和 Tool Call Log 表，正文与可检索审计字段分离。
- 验证测试：创建完整会话运行链路，检查 request、run、session 和 tool 标识能互相追踪。
- 通过标准：可从任一请求定位全部 Agent 步骤和 Tool 调用，敏感正文不会出现在摘要字段。

### 步骤 3.6：建立 Outbox 与写操作草单模型

- 指令：建立 Outbox、Action Draft 和 Approval 占位表，包含事件版本、幂等键、状态、重试次数和过期时间。
- 验证测试：测试同一事务写业务记录与 Outbox、重复幂等键、过期草单和失败重试计数。
- 通过标准：事务要么同时成功要么同时回滚，重复关键写入不会创建多个草单。

### 步骤 3.7：创建首个 Alembic 迁移

- 指令：将全部阶段一核心表、索引、外键、唯一约束和字符集固化为可回滚迁移。
- 验证测试：在空数据库执行升级、降级、再次升级，并比较最终 Schema 与 ORM 元数据。
- 通过标准：三次操作成功，无残留对象，Schema 差异检查为空。

### 步骤 3.8：实现知识仓库基础 Adapter

- 指令：实现文档、版本、Chunk、任务和索引状态的仓库操作，所有查询强制带租户范围。
- 验证测试：运行 CRUD、分页、并发版本创建、跨租户读取和事务回滚集成测试。
- 通过标准：正常操作正确，跨租户读取返回空或权限错误，异常事务不留下半成品。

### 步骤 3.9：实现批量授权后置过滤

- 指令：实现按候选 Chunk ID 批量查询原文并执行租户、ACL、状态、版本和有效期复核。
- 验证测试：混合提交合法、越权、下线、过期、不存在和重复 Chunk ID。
- 通过标准：只返回合法去重结果，并保留输入候选顺序或明确排序规则。

### 里程碑三验证

- 指令：在全新 MySQL 数据库运行迁移和全部仓库集成测试，并更新 `architecture.md` 的表和事务边界。
- 验证测试：模拟索引部分失败后查询 MySQL，确认真理源仍能描述完整失败状态。
- 通过标准：Schema 可重复部署，权限误返回数量为零，架构文档与数据库一致。

- 指令：基于完全虚构的中文电商语料，建立覆盖 FAQ、普通知识、多跳、专有名词、无答案、过期、下线和越权场景的版本化最小评测集，并记录预期 Chunk、实体、引用和可回答性。
- 验证测试：检查每条样本都有唯一标识、输入、角色、预期候选、预期行为和数据版本，且不含真实个人或业务数据。
- 通过标准：最小评测集可重复加载，关键标签无缺失，能在实现检索功能前给出确定的预期结果。

### 步骤 10.1：实现问题规范化

- 指令：对输入执行空白、长度、控制字符和语言基本处理，保留原始问题和规范化问题。
- 验证测试：测试空输入、超长输入、控制字符、中英文、表情和仅标点输入。
- 通过标准：有效问题语义不被破坏，非法问题在调用模型和数据库前被拒绝。

### 步骤 10.2：实现 Query Rewrite

- 指令：结合有限会话历史生成独立问题，设置置信度和回退到原问题的规则。
- 验证测试：测试明确问题、代词指代、历史冲突、无历史、模型失败和恶意指令。
- 通过标准：明确问题不过度改写；失败安全回退；重写不能改变权限或注入系统指令。

### 步骤 10.3：实现向量召回用例

- 指令：以 query 类型生成 Embedding，按租户过滤从 Milvus 召回配置数量的候选。
- 验证测试：使用固定语料测试预期 Top-K、无命中、租户隔离、Embedding 超时和 Milvus 故障。
- 通过标准：预期候选命中，跨租户为零，故障产生明确降级信号。

### 步骤 10.4：实现实体与图谱召回用例

- 指令：抽取查询实体，执行实体匹配和有限跳扩展，返回 Chunk 候选、路径和分数依据。
- 验证测试：测试直接实体、多跳关系、同名歧义、无实体、环图和 Neo4j 故障。
- 通过标准：路径可解释，跳数和租户限制生效，无实体时不会伪造图结果。

### 步骤 10.5：实现关键词召回占位能力

- 指令：通过独立 KeywordRetriever Port 提供 MySQL 文本检索基线，并允许配置关闭。
- 验证测试：测试专有名词、精确编号、常见词、无命中、关闭功能和数据库故障。
- 通过标准：精确词可补充向量召回，关闭时不影响其他召回分支。

### 步骤 10.6：实现并发召回协调

- 指令：并发执行可用召回分支，分别设置超时，保留每路状态和耗时。
- 验证测试：测试全部成功、单路超时、单路异常、全部失败和取消请求。
- 通过标准：单路失败不掩盖其他成功结果；全部失败时不生成无依据答案。

### 步骤 10.7：实现 RRF 融合

- 指令：按候选排名进行 RRF 融合，去重 Chunk，保留来源分支、原排名和融合分数。
- 验证测试：使用固定排名列表测试重叠候选、单路候选、相同分数和输入顺序变化。
- 通过标准：融合结果确定且可解释，不直接比较不同检索器的原始分数。

### 步骤 10.8：接入 MySQL 最终授权过滤

- 指令：将融合候选批量送入 MySQL 复核租户、ACL、状态、版本和有效期，再获取合法原文。
- 验证测试：混合合法、越权、过期、下线、已删除和图谱新增候选。
- 通过标准：任何派生索引候选都不能绕过 MySQL，权限误入上下文数量为零。

### 步骤 10.9：实现 Rerank 与回退

- 指令：对授权后的有限候选执行 Rerank，输出配置数量的最终证据；服务不可用时使用融合顺序回退。
- 验证测试：测试正常重排、候选不足、同分、Rerank 超时、功能关闭和无合法候选。
- 通过标准：证据数量和顺序符合策略，回退可观测，无候选时进入拒答。

### 步骤 10.10：构建证据上下文和引用

- 指令：按 Token 预算组装父子 Chunk、文档标题、版本、更新时间和来源位置，生成稳定引用标识。
- 验证测试：测试预算内、超预算、重复父块、表格、失效引用和多文档证据。
- 通过标准：上下文不超预算，引用可反查合法原文，重复证据被合并。

### 步骤 10.11：实现有证据回答和拒答

- 指令：要求 KB 生成只使用证据内容；无证据、证据冲突或置信度不足时返回明确拒答或澄清。
- 验证测试：测试可回答、无答案、证据不足、证据冲突、知识注入指令和模型幻觉诱导。
- 通过标准：回答中的企业事实均有引用，无答案正确拒答，不执行文档内恶意指令。

### 里程碑十验证

- 指令：运行检索单元、集成和最小 Golden Set，更新 `architecture.md` 的检索时序、降级和权限边界。
- 验证测试：统计 Recall@K、引用正确率、拒答率和权限误召回。

- 指令：通过物流 Port 提供轨迹查询和催单草案，执行频率与幂等检查。

- 验证测试：测试正常金额、超额、重复草单、订单状态变化、草单过期和无权限。

- 通过标准：主流程无需手工修改状态即可完成，失败场景有清晰反馈。

## 16. 里程碑十四：可观测性、安全、评测与交付

### 步骤 14.1：接入 Langfuse Trace

- 指令：为 API、Supervisor、Agent、检索分支、授权、Rerank、Tool 和模型调用建立同一 Trace 下的 Span。
- 验证测试：完成一次 FAQ、一次 KB、多 Agent 和一次失败请求，检查 Trace 层级、耗时和关联标识。
- 通过标准：每条请求可完整追踪，不上传密钥和未经脱敏的敏感正文。

### 步骤 14.2：实现统一脱敏

- 指令：在日志、Trace、审计和错误响应前统一处理手机号、地址、订单号、Token 和密钥模式。
- 验证测试：向各入口注入标记过的敏感样本，并搜索日志、Trace 测试导出和 API 响应。
- 通过标准：敏感原值不出现在任何受检输出中，业务追踪标识仍可关联。

### 步骤 14.3：加固 JWT 与 RBAC 闭环

- 指令：复核步骤 12.2 的身份接入以及上传、会话、调试、检索和 Tool 的授权点，补充 Key 轮换、缓存失效、安全审计和生产配置门禁。
- 验证测试：测试合法 Token、过期、错误签名、未知 Key、Key 轮换、无角色、跨租户、角色提升、生产测试身份和授权审计缺失。
- 通过标准：非法身份统一拒绝，角色不能由请求正文自行声明，跨租户访问为零，生产环境不存在测试身份旁路，每次拒绝都有脱敏审计记录。

### 步骤 14.4：建立 Prompt Injection 防护测试

- 指令：建立用户输入和知识文档中的越权、忽略系统指令、索取密钥、诱导工具调用和伪造引用样本。
- 验证测试：让 FAQ、KB、Supervisor 和 Tool 流程分别处理全部攻击样本。
- 通过标准：攻击不能改变权限、系统规则或 Tool 风险级别，失败被记录为安全事件。

### 步骤 14.5：扩充完整 Golden Set

- 指令：在步骤 10.0 的最小合成 Golden Set 上扩充 FAQ、普通知识、多跳、专有名词、多轮指代、无答案、过期、下线、越权、多意图、情绪升级和 Prompt Injection 场景。
- 验证测试：检查每条样本都包含预期意图、Agent、Chunk、实体、可回答性、角色和行为标签。
- 通过标准：没有缺失关键标签的样本；评测集不含真实敏感业务数据。

### 步骤 14.6：实现离线评测

- 指令：计算路由准确率、Recall@K、MRR、NDCG、引用正确率、Faithfulness、拒答率、任务成功率和 P95 延迟。
- 验证测试：使用人工构造的全对、全错和部分正确结果验证每个指标计算。
- 通过标准：指标与人工计算一致，评测报告记录数据集、模型、Prompt、知识和代码版本。

### 步骤 14.7：建立依赖故障演练

- 指令：分别模拟 MySQL、Redis、Milvus、Neo4j、LLM 和 Reranker 不可用，验证既定降级和 fail-closed 行为。
- 验证测试：对每个依赖执行单故障和关键组合故障场景。
- 通过标准：权限系统和 MySQL 不可用时不返回知识；其他依赖按文档降级；没有无限重试。

### 步骤 14.8：建立完整 CI

- 指令：扩展步骤 1.11 的基础 CI，加入契约测试、数据库集成测试、前端测试、生产构建、容器扫描和端到端测试，并按资源消耗区分快速门禁与完整门禁。
- 验证测试：分别提交格式错误、类型错误、失败测试、泄露测试密钥、漏洞依赖和正常变更验证门禁。
- 通过标准：错误变更在对应阶段被阻断；正常变更全部通过；CI 不调用收费模型。

### 步骤 14.9：建立生产镜像

- 指令：创建后端和前端多阶段镜像，使用非 root 用户、固定基础镜像、最小运行依赖和健康检查。
- 验证测试：扫描镜像、检查运行用户、启动容器、执行健康检查并尝试写入只读应用目录。
- 通过标准：容器以非 root 运行，无高危未处理漏洞，只有数据目录可写。

### 步骤 14.10：建立一键验收流程

- 指令：整理本地依赖启动、迁移、示例数据入库、应用启动、Smoke Test 和清理顺序。
- 验证测试：在全新环境由另一位开发者按文档完成完整流程，不使用实现者机器上的隐藏状态。
- 通过标准：流程可重复，失败点有诊断信息，清理不会删除未授权数据。

### 步骤 14.11：完成阶段一安全验收

- 指令：复核默认密码、Fake 开关、上传限制、权限、跨租户、日志脱敏、Tool 风险和退款草单边界。
- 验证测试：使用生产配置启动，尝试启用 Fake、使用默认凭据、越权检索和提交真实退款。
- 通过标准：所有危险配置和操作均被拒绝，系统没有真实资金写入路径。

### 步骤 14.12：完成文档与 AI 交接

- 指令：更新 README、`architecture.md`、作为权威设计文档的 `phase1_env_checklist.md`、API 说明、数据模型、故障排查、评测报告和 `progress.md`，确保只描述当前真实能力，且不得创建重复的 `design-document.md`。

- 通过标准：回答无需猜测关键路径；所有文档链接有效；已完成与未完成事项清晰分离。

### 里程碑十四验证

- 验证测试：在干净环境完成一次完整演示，并随机抽取三条失败场景复验。
- 通过标准：所有阶段一验收门槛达标，权限误召回为零，阶段二可通过新增 Adapter 和部署单元继续实施。

## 17. 阶段一结束后的阶段二入口

阶段一验收通过前不得执行以下步骤。阶段二开始时，应基于已有 Port 和事件契约分别创建新的计划，不在本计划中直接实现：

- 用 Kafka Event Publisher 替换进程内发布，并启用 Outbox Relay、消费者幂等和 DLQ。
- 用 S3 兼容 Object Store 替换本地对象存储。
- 将订单、物流和退款 Fake Adapter 替换为真实业务 API Adapter。
- 在退款草单之后接入真实审批中断与回调恢复。
- 根据负载证据拆分入库 Worker、检索服务和 Tool 服务。
- 建立多租户配额、生产监控、灾备和发布门禁。

阶段二入口验证：

- 指令：选择任一 Fake Adapter，以测试替身模拟真实 Adapter 替换过程，确认 Agent、API 和领域模型无需修改。
- 验证测试：运行替换前后的契约测试和端到端测试并比较外部行为。
- 通过标准：除基础设施组装和配置外不需要修改核心业务代码，证明阶段一预留边界有效。
